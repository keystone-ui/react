## Features

- **Collapsible sidebar shell** with an icon rail, grouped navigation, a badge, and a footer account row.
- **Topbar** with a sidebar trigger and a [breadcrumb](/docs/components/breadcrumb).
- **Overview** with a KPI row and a stacked signups chart sharing the same toggleable legend as [`dashboard-01`](/docs/blocks/dashboard-01).
- **Two tables, one design**: Users and Payments share the same toolbar, header, skeleton, empty state, footer and selection bar, built from the same parts over two filter vocabularies.
- **Filter pills**: every filter is a self-describing pill (`Role: Admin`, `Action: Deposit`). Two are on the row from the start, and you add the rest from `+ Add filter`. Payments' Currency, Amount and Player are Notion-style operator chips (`Currency is not: BTC`, `Amount: > 100`, `Player does not contain: gmail`).
- **View controls**: at the far end of the row, `Columns` hides and shows columns, `Export` downloads the filtered result as CSV, and `Sort` orders by any sortable column in words that fit it (`Newest first`, `Largest first`, `A–Z`). The headers sort the same state.
- **Row selection**: a checkbox column and a [`SelectionBar`](/docs/components/selection-bar) whose actions (export the selection, copy its ids) run.
- **Loading**: every change goes through a stand-in request, with [`Skeleton`](/docs/components/skeleton) rows at the real rows' height while it's in flight.
- **Shareable views**: the open section, filters, sort and page live in the URL, so a link or a reload lands on the same rows.
- **Payments details**: amounts grouped at their currency's precision, a record that opens in a side [`Drawer`](/docs/components/drawer), and an [`Empty`](/docs/components/empty) state that offers `Clear filters`.
- **Mobile filters**: below `sm` both tables fold their pills, view controls and sort into the same bottom-sheet `Drawer` and [`Stepper`](/docs/components/stepper) drilldown.
- **User detail**: clicking a name opens a read-only record view built from [`DescriptionList`](/docs/components/description-list), with [`CopyButton`](/docs/components/copy-button) on the values you'd paste elsewhere.

[Filter and table patterns](/docs/concepts/filter-and-table-patterns) explains the design behind these tables: why the filters are pills, how operators are chosen, how sorting, selection, loading and the URL behave, and what changes below `sm`.

## Requirements

The sidebar is **shadcn's, adapted onto Keystone UI's primitives**, and ships inside the block as `components/sidebar.tsx`. Keystone UI ships no app shell in the library on purpose. [Keystone UI and shadcn](/docs/concepts/keystone-and-shadcn) explains why, and the [sidebar reference](/docs/reference/shadcn-sidebar) covers how the sidebar behaves: its keyboard shortcut, its `sidebar_state` cookie and its drawer on phones.

Don't also run `shadcn add sidebar`. The bare name selects shadcn's item, whose dependencies install to the same paths as Keystone UI's Button, Input and Tooltip. Accepting an overwrite (or passing `--overwrite`) replaces Keystone UI's files with the selected shadcn style's versions.

The sidebar reads 6 `--sidebar-*` tokens (`--sidebar`, `--sidebar-foreground`, `--sidebar-accent`, `--sidebar-accent-foreground`, `--sidebar-border`, `--sidebar-ring`). Keystone UI's style item declares all 8 of the set as aliases of your theme tokens, so the sidebar follows whichever Keystone UI theme is active.

**`SidebarInset` carries `min-w-0`.** The sidebar file sets it, so the wide users table shrinks inside the inset instead of giving the whole document a horizontal scrollbar. Keep it if you restyle the inset.

### Files shared with dashboard-01

Four files are duplicated byte for byte from [`dashboard-01`](/docs/blocks/dashboard-01) rather than shared through a common registry item: `chart.tsx`, `chart-formatters.ts`, `series-legend.tsx` and `use-reduced-motion.ts`.

A block's installable copy is flat: every component lands at `@/components/<basename>.tsx`, so two blocks shipping a `chart.tsx` write to the same path, and installing both is last-writer-wins. A registry item of their own would have put chart code back on the installable component surface, which keeping recharts a *block* dependency avoids.

`apps/docs/tests/block-shared-files.test.ts` asserts the copies are byte-identical, and fails if a new basename starts colliding without being classified. Only infrastructure is shared this way. The panels and fixtures are each block's own, because two blocks sharing those would be the same demo twice.

## Data table hook

Both tables get their state from `useDataTable` in `use-data-table.ts`.

### What `useDataTable` asks for

`DataTableConfig` in `use-data-table.ts` takes the fields below. Each row needs a string `id`; selection is keyed on it.

- `rows`: every row the table can show.
- `matches(row, filters)`: whether one row passes the current filters.
- `sortRows(rows, sort)`: returns the rows in `sort` order.
- `emptyFilters`: the filter state with nothing applied. The table starts on it, and `Clear all` returns to it.
- `defaultKeys`: the pills on a fresh row. `Clear all` puts these back.
- `defaultSort`: the sort the table opens on.
- `defaultPageSize`: the page size the table opens on.
- `clearFor(key)`: a filter's reset patch, applied when its pill is removed.
- `latency`: how long the stand-in request takes, in milliseconds. Optional; 300 when left out.

### Where filtering runs

Filtering, sorting and paging all run in the browser, over the whole `rows` array. The function `run` in `use-data-table.ts` filters with `matches`, sorts with `sortRows`, and slices out the current page.

There is no request: `useSimulatedFetch`, in the same file, stands in for one. It computes `run` and returns the answer after `latency`, so the skeleton rows have a loading state to show. [Filter and page the users table on the server](/docs/guides/page-the-users-table-on-the-server) replaces it with your data layer.
