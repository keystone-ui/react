## Features

- **Collapsible sidebar shell** with an icon rail, grouped navigation, a badge, and a footer account row.
- **Topbar** with a sidebar trigger and a [breadcrumb](/docs/components/breadcrumb).
- **Overview** with a KPI row and a stacked signups chart sharing the same toggleable legend as [`dashboard-01`](/docs/blocks/dashboard-01).
- **Users table** — a responsive filter toolbar (search, role, status, sort), sortable columns, row selection, pagination, and a [`SelectionBar`](/docs/components/selection-bar) for bulk actions.
- **Payments** — a wide transaction table with eleven filters: the three most-used inline, the rest behind a panel, and everything applied shown as a removable chip.
- **Mobile filters** — below `sm` the cluster collapses into a single Filters button opening a bottom-sheet [`Drawer`](/docs/components/drawer), with a [`Stepper`](/docs/components/stepper) drilling into one screen per filter.
- **User detail** — clicking a name opens a read-only record view built from [`DescriptionList`](/docs/components/description-list), with [`CopyButton`](/docs/components/copy-button) on the values that exist to be pasted elsewhere.

## Requirements

The sidebar is **shadcn's, not keystone's**. Keystone deliberately ships no app shell — see [Using shadcn Components](/docs/interop) for why, and for the two things you have to get right when mixing the registries.

Installing this block pulls it in through `registryDependencies`, but if you are composing by hand:

```bash
npx shadcn@latest add sidebar
```

Two consequences worth knowing before you do:

**Delete the `--sidebar-*` block that `shadcn add` appends to your CSS.** Keystone already declares those eight tokens as aliases of your theme tokens, so the sidebar follows whichever keystone theme is active. shadcn's injected values are hardcoded neutral and land *after* keystone's, so they win — and your sidebar renders grey inside a slate app.

**`SidebarInset` needs `min-w-0`.** Not cosmetic: without it the wide users table pushes the inset open and the whole document gains a horizontal scrollbar. Keystone bakes this into components it owns; it cannot for a file it does not.

```tsx
<SidebarInset className="min-w-0">
```

## Shared with dashboard-01, byte for byte

Four files — `chart.tsx`, `chart-formatters.ts`, `series-legend.tsx`, `use-reduced-motion.ts` — are duplicated verbatim from [`dashboard-01`](/docs/blocks/dashboard-01) rather than shared through a common registry item.

That is deliberate. A block's installable copy is flat: every component lands at `@/components/<basename>.tsx`, so two blocks shipping a `chart.tsx` write to the same path and installing both is last-writer-wins. Hoisting them into their own registry item would have put chart code back on the installable component surface, which is exactly what keeping recharts a *block* dependency avoids.

So they are duplicated and the duplication is enforced: `apps/docs/tests/block-shared-files.test.ts` asserts the copies are byte-identical and fails if a new basename starts colliding without being classified. Only infrastructure is shared this way — the panels and fixtures are each block's own, because two blocks sharing those would be the same demo twice.

## Notes

**Why the payments filters are a panel and not a rail.** A filter sidebar is the obvious answer to eleven filters, and it is the wrong one for this table. The payments columns need about 1050px; the content area is 1024px at a 1280px viewport, so the table is already short before anything is taken from it. A 300px rail would leave 724px — a third less than the columns need — and force horizontal scrolling on a standard laptop. A panel costs nothing until it is opened.

That trade is table-shaped, not universal: a rail works well beside a narrow single-column list, which is why chat and mail apps use one.

**The chips are what make a panel acceptable.** A filter you cannot see is a filter you forget you set, and the question that follows is always "why am I looking at four rows?". Every applied filter appears as a removable chip under the toolbar whether the panel is open or shut, and each removes only itself — selected currencies expand to one chip each, because dropping one value from a multi-select is a different action from clearing the whole thing.

The Filters button counts only what lives in the panel. Type and status have their own controls in the toolbar, and counting a filter you can already see would make the badge read as a second, contradictory signal.

One panel serves both breakpoints. `Drawer`'s `swipeDirection="right"` is already responsive — 75% of the width on a phone, a floating panel at `md` — so there is no media query and nothing to get wrong on the server.

Payment ids are middle-truncated in the table with a copy button, and shown in full on the record. The head and tail are what you eyeball against a provider's dashboard; the whole value is what you paste into it.

**The detail view is a sub-state of Users, not a section of its own.** A new section would need a sidebar entry — and you cannot navigate to a detail page with no record chosen — so the open user is a separate `openUserId`, resolved to a record at render. Changing section clears it, or leaving to Billing and returning would land on a stale record.

The breadcrumb reflects that: with a record open, `Users` stops being the page and becomes the way back to the list, with the user's name as the terminal crumb.

Values are stacked above their labels in two columns — `DescriptionList`'s `orientation="stacked"`, with the grid itself in `className`. Its default row layout right-aligns each value against its label, which reads as a summary; a record wants the label to sit above the value it describes. A field the record does not have renders `-` rather than being omitted, so the grid keeps its alignment.

Rows reveal an **Open** button on hover, as [`tickets-01`](/docs/blocks/tickets-01) does. It carries `focus-visible:opacity-100` alongside `group-hover/row:opacity-100` — without that second rule a hover-revealed control is mouse-only. The name stays clickable too, so the affordance does not depend on discovering the hover.

`invitedBy` stores the inviter's **id**, not their name, so **Invited by** links to that user's record rather than naming it as dead text. A detail page that mentions another record it can already open should take you there.

The header spans the full width with the actions at its right edge, while the card is capped — so the buttons reach the container without the record's two columns drifting apart on a wide screen. Sections carry their own padding and the card's is zeroed, which lets the rules between them run the full width of the card instead of stopping short of its edges.

**The toolbar forks at `sm:`, following [`tickets-01`](/docs/blocks/tickets-01).** Search is shared and always visible; the filter cluster is `hidden sm:flex`, and below that a single Filters button opens a bottom-sheet drawer. The fork is CSS-only — both trees are always mounted, so there is no `useMediaQuery` to get wrong on the server, and no flash of the wrong layout during hydration.

The drawer's body is a [`Stepper`](/docs/components/stepper): a menu of "label + current value" rows that drill into one `RadioGroup` screen per filter, with a back arrow and an Apply footer. Filters apply **live** — `Apply` only dismisses, there is no draft state to reconcile.

One thing `tickets-01` has is deliberately left out: **no column-visibility menu.** Six columns do not earn one, and that block already demonstrates the pattern.

The **Clear** button only renders when something is actually filtered, and carries the count. A permanently visible "Clear" on an unfiltered table is a control that does nothing, and it hides the one signal that a filter is on. Since that button is desktop-only, the mobile trigger carries the count as a badge and the drawer footer gains a **Clear all** — otherwise a filtered table on a phone gives no sign that anything is filtering it.

**Sorting is one piece of state, not two.** The toolbar's Sort menu and the column headers write the same `sort` value, so picking "Name Z–A" moves the header arrow and clicking a header updates the menu's label, with no syncing code. `SORT_OPTIONS` therefore lists every key × direction pair the headers can reach — a state the headers could produce but the toolbar could not name would leave the radio group with nothing selected.

Every control in the row sits on the **40px** `default` tier, with no `size` props. Anything added to the row should stay on that tier — mixing sizes between neighbours is the usual cause of a toolbar that looks subtly off.

The filter menus are [`DropdownMenuRadioGroup`](/docs/components/dropdown-menu#radio-group), not checkbox items — each filter is single-select, so picking a value closes the menu. That is keystone's default for radio items and the reason a second filter is clickable straight after the first; a menu left open holds an inert overlay across the page that swallows the next click.

Every filter change resets `pageIndex` to 0. Page 2 of the unfiltered list usually does not exist once a filter is applied, and a table reading "Page 2 of 1" with no rows looks broken.

Select-all is binary rather than tri-state. Keystone's [`Checkbox`](/docs/components/checkbox) has no indeterminate variant, and re-implementing the custom mixed-state control that [`tickets-01`](/docs/blocks/tickets-01) uses would duplicate a workaround rather than share one.

The Status column passes **no** `sortDirection` at all, where the sortable columns pass `null`. That distinction is the point of the three-way prop: omitted means the column does not sort and emits no `aria-sort`, while `null` means sortable but not currently active.
