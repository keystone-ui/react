Keystone UI has partial right-to-left support. This guide covers app setup and
known component limitations, so you can judge whether the library fits an RTL
product before you build on it.

## Summary

| Area | Status |
| --- | --- |
| Base UI keyboard nav and popup positioning | Popups normally inherit direction from the root. Above or below the trigger, `start`/`end` follow the positioner's computed direction. A `DirectionProvider` maps horizontal arrow keys and `inline-*` sides |
| Keystone's own spacing and positioning CSS | Many one-sided gutters, offsets and text alignments keep their physical side |
| Explicit `rtl:` handling in the library | Calendar's default month navigation chevrons |
| i18n / locale / message layer | No locale layer; [`StringsProvider`](/docs/components/strings) replaces some built-in English |
| RTL tests or visual baselines | Targeted right-to-left checks for some components; Storybook snapshot comparison of RTL examples such as Reel |

## What works

Components built on [Base UI](https://base-ui.com) inherit its
direction-aware behavior where it applies: horizontal arrow-key navigation, the
`inline-start`/`inline-end` popup sides, and slider axis handling. Base UI reads
the reading direction for these from its own context, which defaults to `ltr`.
Popup alignment works differently. Above or below the trigger, `start` and `end`
use the positioner's computed direction, normally inherited from the root.
Beside the trigger, `start` uses the top edge in either reading direction.
Alignment offsets and collision handling can move the popup from that edge.
Select's item-aligned mode uses the provider's direction. Drawer swipe
directions stay physical (`left`, `right`, `up`, `down`), so choose
`swipeDirection` for your layout.

Set the direction on the root element (`<html dir="rtl">`), and wrap your app
in Base UI's `DirectionProvider`. For a package install, add `@base-ui/react`
as a direct dependency at the version Keystone uses. Make sure your app's
provider and Keystone's components load the same Base UI module instance.

```tsx
import { DirectionProvider } from "@base-ui/react/direction-provider";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html dir="rtl">
      <body>
        <DirectionProvider direction="rtl">{children}</DirectionProvider>
      </body>
    </html>
  );
}
```

The two do different jobs. Set the root direction for popup layout and the
provider direction for Base UI's horizontal arrow navigation (including the key
that opens a submenu) and logical popup sides. Pass `dir="rtl"` to Calendar
itself for its day-grid arrow keys.

**A `dir` on a wrapper element is not enough for popups.** A top-level popup (a
menu, select, combobox, popover, tooltip, modal or drawer) uses a body portal by
default. If only the trigger's wrapper is RTL on an LTR page, that portal still
inherits LTR, even with the provider.

## What does not work

**Many one-sided gutters, offsets and text alignments keep their physical side
in RTL.** They use physical utilities (`pl-`, `pr-`, `ml-`, `mr-`, `left-`,
`right-`, `text-left`, `text-right`), which do not respond to `dir`. For
example, from `sm` up, the Modal header stays left-aligned and the footer
actions align at the inline end.

Calendar uses `rtl:` variants for its default month navigation chevrons. Reel uses
logical positioning for its arrows and the scroller's computed direction for
paging. Its chevrons and the horizontal fade follow the nearest explicit
`dir="ltr"` or `dir="rtl"`. `FileUploadItemName` sets `dir="auto"` so a file
name keeps its own direction.
RollingNumber's direction and numbering systems are covered in
[its RTL section](/docs/components/rolling-number#rtl).

**There is no full i18n layer.** Keystone ships no locale plumbing.
[`StringsProvider`](/docs/components/strings) replaces some of the library's
built-in English; its page lists the text it covers. For package installs, check
that your version exports `@keystoneui/react/strings`.
`RollingNumber` formats its number with `Intl.NumberFormat` and the
`locale` you pass. The default locale is `en-US`. Other components have their
own defaults, such as the month formatter in `Calendar` and the byte formatter
in `FileUploadItemSize`.

**RTL test coverage is partial.** Unit tests press arrow keys inside a
right-to-left `DirectionProvider` for FilterChips, ToggleGroup and TagGroup.
Chromium Storybook tests check, among others, Reel paging and the painted fade in
both directions, a DropdownMenu submenu's side and keys, and the layout of Tag,
Countdown and TablePagination in a right-to-left container. The docs end-to-end
tests check Reel's built stylesheet, arrow placement and paging across nested
direction settings, and scrollable Tabs in right-to-left. Storybook is
configured to compare snapshots of RTL examples such as Reel.

## Working around it today

Use these options where a component keeps its physical layout:

- When the part that owns a utility exposes `className`, pass the override
  there. For an internal element with a `data-slot`, target that slot in your
  CSS. On `ModalHeader`, `sm:text-start` replaces `sm:text-left`. For single
  edges, `ps-4` leaves `pl-4` in place. To move that padding to the right in an
  RTL-only layout, use `pl-0 pr-4`.
- Restrict RTL to layouts you compose yourself and keep Keystone components in
  direction-neutral positions.
- Set the root direction for popup layout and the provider direction for Base
  UI's horizontal arrow navigation and logical popup sides, as shown above. Pass
  `dir="rtl"` to Calendar itself for its day-grid arrow keys, and accept the
  visual mirroring gaps.

## Contributing

Convert spacing and offsets that should follow reading order (`pl-`/`pr-` to
`ps-`/`pe-`, `ml-`/`mr-` to `ms-`/`me-`, `left-`/`right-` to `start-`/`end-`).
Keep offsets tied to a physical gesture on that edge, such as a Drawer's swipe
side. See
[CONTRIBUTING.md](https://github.com/keystone-ui/react/blob/main/CONTRIBUTING.md).
