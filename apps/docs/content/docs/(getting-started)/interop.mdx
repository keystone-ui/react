title: Using shadcn Components
description: Keystone is a shadcn-compatible registry, so components it does not ship can come from shadcn's — here is what that costs and how to make it look right.
---

Keystone installs to the same paths shadcn does (`@/components/ui/*`, `@/lib/utils`) and uses the same registry format. Anything keystone does not ship you can install from shadcn's registry, side by side.

## Both libraries are on Base UI now

Since July 2026, [shadcn's default base is Base UI](https://ui.shadcn.com/docs/changelog) — the same primitives keystone has always used. New shadcn projects get it unless they opt out with `shadcn init -b radix`.

That makes mixing the two far less interesting than it used to be. A shadcn component installed next to keystone wraps the same primitive, exposes the same `render` prop rather than Radix's `asChild`, and carries the same accessibility semantics. The differences left are visual, not behavioural.

Two things follow:

- **Check which base a project is on before copying shadcn snippets into it.** A Radix-era snippet uses `asChild`; keystone and Base-UI-era shadcn both use `render`. The rename is mechanical, but it is silent — `asChild` on a Base UI component is an unknown prop, not an error.
- **Radix is not deprecated.** shadcn still ships every component for it, so a snippet you find may be written either way.

## What keystone deliberately does not ship

**Sidebar.** An app shell is a large, opinionated component — a collapsible icon rail, a mobile drawer, persisted state, a keyboard shortcut, and a `peer`/`group` layout contract between four parts. shadcn's is good, widely understood, and already maintained. Reimplementing it would mean owning ~900 lines to arrive somewhere very close.

So keystone's sidebar is shadcn's, adapted onto keystone's Button, Drawer, Input, Separator, Skeleton and Tooltip. It is a registry item, not a library export: one file, `components/sidebar.tsx`, installed on its own or as part of [`admin-01`](/docs/blocks/admin-01). See [The sidebar item](#the-sidebar-item) below, and do not run `shadcn add sidebar`.

**Charts.** A chart wrapper is mostly a list of `[&_.recharts-*]` overrides that make recharts' hardcoded `#ccc` and `#fff` marks respect your theme — archaeology, not something worth re-deriving. The real reason it stays out of `@keystoneui/react` is recharts itself: a chart is one screen in most apps, and a library dependency would bill every other screen for it.

```bash
npx shadcn@latest add chart
```

Keystone's own `dashboard-01` and `admin-01` blocks vendor that file rather than importing it from the library, for the same reason. Two changes in those copies are worth carrying into yours, because upstream does not have them:

```diff
- <div className="aspect-video ...">
+ <div className="aspect-auto min-w-0 ...">
```

- **`aspect-auto`, not `aspect-video`.** Under an explicit pixel height the upstream class still imposes a 462px floor, which overflows the row and gives the whole document a horizontal scrollbar.
- **`min-w-0`.** A chart is usually a grid or flex child, and those default to `min-content` — without it a wide chart pushes its container open instead of shrinking.

shadcn's `chart` item lists `card` as a registry dependency. That is harmless here: `shadcn add` skips files that already exist, so keystone's [`Card`](/docs/components/card) stays.

## Making it match your theme

shadcn defines eight `--sidebar-*` tokens for its sidebar. Keystone's style item declares all eight, as **aliases** of your theme tokens:

```css
--sidebar: color-mix(in oklch, var(--background) 97%, var(--foreground));
--sidebar-foreground: var(--foreground);
--sidebar-primary: var(--primary);
--sidebar-primary-foreground: var(--primary-foreground);
--sidebar-accent: var(--accent);
--sidebar-accent-foreground: var(--accent-foreground);
--sidebar-border: var(--border);
--sidebar-ring: var(--ring);
```

Because they are aliases rather than literals, the sidebar follows whichever keystone theme is active — pick `slate` and the sidebar goes slate too. Only `--sidebar` needs a dark override, since its formula differs rather than its inputs.

<Callout type="warn">
`npx shadcn add sidebar` appends **its own** `--sidebar-*` block to your CSS, with shadcn's neutral values hardcoded. Because it lands after keystone's, it wins — and your sidebar renders neutral grey inside a slate app.

**Delete the injected block.** It is the last `--sidebar-*` group in your `globals.css` after running the command.
</Callout>

## `SidebarInset` carries `min-w-0`

Keystone's `components/sidebar.tsx` sets `min-w-0` on `SidebarInset` itself, so you do not need to add it. Keep it if you restyle the inset, and add it at the call site if you use a sidebar file that does not set it:

```tsx
<SidebarInset className="min-w-0">
```

Not cosmetic. A flex item will not shrink below its content's intrinsic width, so without it any wide child — a table, a chart, a long unbroken string — pushes the inset open and the whole document gains a horizontal scrollbar. In the app this pattern was taken from, the omission produced **+256px of overflow across eight pages, at every width from 768 to 1600**, and went unnoticed until a test measured it.

## Which registry a dependency resolves against

A registry item's `registryDependencies` may name items by bare name (`"button"`) or by namespace (`"@keystone/button"`). Bare names resolve against shadcn's registry, so configure the namespace if you want keystone's:

```json title="components.json"
{
  "registries": {
    "@keystone": "https://keystoneui.io/r/{name}.json"
  }
}
```

```bash
npx shadcn@latest add @keystone/button
```

Both registries write to the same paths, so the distinction matters. `shadcn add` skips a file that already exists, which protects an app that installed keystone's `button.tsx` *earlier* — but not one command that resolves both: an item that pulls shadcn's `button` and keystone's in the same run writes one of them, and it was shadcn's when we measured. That is why every keystone item names its keystone dependencies by full URL (`https://keystoneui.io/r/button.json`), never by bare name.

You can also declare registries in `package.json` instead of `components.json` — shadcn reads both, and merges them.

### Toast is the one real collision

shadcn now ships its own Base UI [Toast](https://ui.shadcn.com/docs/components/base/toast), and it writes to `toast.tsx` — the same path as keystone's. Whichever is installed first wins, silently, and the two have different APIs.

Use keystone's and do not run `shadcn add toast`. If you already did, delete the file and reinstall `@keystone/toast`. shadcn's Sonner still exists in the registry but has lost its docs page, so treat it as on the way out rather than as the alternative.

## Control heights differ

Keystone's controls are **40px** at their default size. shadcn's depend on the style you install — they have run 32px to 40px across the eight current ones, so check rather than assume.

Because keystone's files win the path collision above, a shadcn component that composes `Button` renders keystone's height inside a layout built for shadcn's. It only shows when the two sit in the same row.

Both libraries expose `sm` at 32px, so a mixed toolbar is most reliable with `size="sm"` throughout.

## The sidebar item

```bash
npx shadcn@latest add https://keystoneui.io/r/sidebar.json
```

<Callout type="warn">
Use the full URL. The bare name `sidebar` selects **shadcn's** item, whose dependencies include its Button, Input, Separator, Skeleton and Tooltip, which install to the same paths as keystone's files. Accepting the CLI's offer to overwrite them, or passing `--overwrite`, replaces keystone's files with the selected shadcn style's versions. That is what happened when `admin-01` depended on shadcn's item: installing the block replaced keystone's files with Radix ones.
</Callout>

It writes `sidebar.tsx` under your components alias (`components/sidebar.tsx` by default) and installs keystone's Button, Drawer, Input, Separator, Skeleton and Tooltip beside it. It is the same file [`admin-01`](/docs/blocks/admin-01) installs, so an app that adds both from the same release gets identical bytes at that path. If you edit your copy (the drawer's name, the cookie line, the shortcut), a later `add` of `sidebar` or `admin-01` finds a file that differs and offers to overwrite it; accepting, or passing `--overwrite`, discards your edits.

It reads six `--sidebar-*` tokens: `--sidebar`, `--sidebar-foreground`, `--sidebar-accent`, `--sidebar-accent-foreground`, `--sidebar-border` and `--sidebar-ring`. The default style at `https://keystoneui.io/r/default.json` and the manual CSS in the [quick start](/docs/installation/quick-start) declare all eight of the set ([above](#making-it-match-your-theme)); `@keystoneui/react/base.css` declares none, so an app that imports only `base.css` gets a sidebar with no surface or hover colours.

This is the vendored version: it imports your local keystone components through the UI alias in `components.json` (normally `@/components/ui`). In an app that imports components from the `@keystoneui/react` package instead, install the package flavour. It writes the same `sidebar.tsx`, importing `@keystoneui/react/*`:

```bash
npx shadcn@latest add https://keystoneui.io/r/npm/sidebar.json
```

It is tested with `@keystoneui/react` 1.0.0-beta.11 and needs a `components.json` ([Apps that use the npm package](/docs/blocks/users-01#apps-that-use-the-npm-package) gives one). It installs `@base-ui/react` unpinned: keep your `@base-ui/react` at the version `@keystoneui/react` pins. Pick one flavour per app.

### Composition

```tsx
import { House as HouseIcon } from "lucide-react";
import type { ReactNode } from "react";
import {
  Sidebar,
  SidebarContent,
  SidebarGroup,
  SidebarGroupLabel,
  SidebarInset,
  SidebarMenu,
  SidebarMenuButton,
  SidebarMenuItem,
  SidebarProvider,
  SidebarRail,
  SidebarTrigger,
} from "@/components/sidebar";

export function AppShell({ children }: { children: ReactNode }) {
  return (
    <SidebarProvider>
      <Sidebar collapsible="icon">
        <SidebarContent>
          <SidebarGroup>
            <SidebarGroupLabel>Workspace</SidebarGroupLabel>
            <SidebarMenu>
              <SidebarMenuItem>
                <SidebarMenuButton isActive render={<a href="/" />} tooltip="Home">
                  <HouseIcon />
                  <span>Home</span>
                </SidebarMenuButton>
              </SidebarMenuItem>
            </SidebarMenu>
          </SidebarGroup>
        </SidebarContent>
        <SidebarRail />
      </Sidebar>
      <SidebarInset>
        <header className="flex h-14 items-center px-4">
          <SidebarTrigger />
        </header>
        {children}
      </SidebarInset>
    </SidebarProvider>
  );
}
```

`SidebarMenuButton` is a `<button>` unless you pass `render`; which item is active is yours to decide, through `isActive`.

### How it behaves

- **Collapsing.** `<Sidebar>` defaults to `collapsible="offcanvas"`: collapsed, it slides fully off-screen. `collapsible="icon"` leaves a rail of icons instead (3rem wide in the default `variant`), and each `SidebarMenuButton`'s `tooltip` shows only while the sidebar is collapsed and not on a phone. `collapsible="none"` renders a static column at every width: no collapse, no drawer on phones, and not `fixed`. The open state lives in the provider, so the shortcut and the cookie work even with `collapsible="none"`, where the column itself does not move. Expanded, the sidebar is 16rem wide; `variant` is `sidebar`, `floating` or `inset`, and `side` is `left` or `right`.
- **Phones.** Below 768px the sidebar renders inside keystone's [`Drawer`](/docs/components/drawer), opening from its `side`, 18rem wide at every phone width (`SIDEBAR_WIDTH_MOBILE`) rather than at the Drawer's own three quarters of the viewport. The drawer's accessible name is a visually hidden "Sidebar", in English; change it in your copy of the file. The server renders the desktop markup, which is hidden below `md`, and the phone layout takes over after hydration.
- **Keyboard.** Cmd+B or Ctrl+B toggles the sidebar from anywhere on the page; on desktop it collapses and expands without animation, and on a phone it opens and closes the drawer. The listener is on `window`, in the bubble phase, and calls `preventDefault()` even when focus is in a text field: pressing Cmd/Ctrl+B in an editor toggles the sidebar too, unless the editor stops the event from propagating, and cancels the browser's own default for the key, so it can conflict with an editor's bold. To change the key, edit `SIDEBAR_KEYBOARD_SHORTCUT` in your copy; to remove the shortcut, delete the effect that adds the `keydown` listener. `SidebarTrigger` is a button in the tab order; `SidebarRail` toggles on click and is left out of it.
- **The `sidebar_state` cookie.** Only the provider's own `setOpen` writes it. The desktop trigger, the rail and the shortcut call it, and so does `setOpen` from `useSidebar()`, on any viewport. Each call writes the value it asked for, `sidebar_state=true` or `sidebar_state=false`, with `path=/` and a lifetime of seven days (`max-age=604800`). The default state writes nothing. The phone drawer keeps separate state: opening or closing it never writes the cookie or calls `onOpenChange`. The file never reads the cookie back: to restore the state on the next load, read it on the server and pass it to `SidebarProvider` as `defaultOpen`. To stop the writes, remove the `document.cookie` line from your copy.
- **Controlled state.** With `open` and `onOpenChange`, each `setOpen` call hands the requested value to `onOpenChange` and still writes it to the cookie, even if your callback ignores it; a change you make to `open` yourself writes nothing, so the cookie can disagree with the screen. `onOpenChange` without `open` freezes the desktop sidebar: the request goes to your callback and the provider's own state never changes. `open` governs the desktop state only; the phone drawer does not follow it.
- **Reduced motion.** Every sidebar transition is timed by `--duration-fast` or `--duration-base` from `base.css`, which drop to 0.01ms under `prefers-reduced-motion: reduce`, so collapsing and hover colours change at once. The phone drawer follows `Drawer`'s own motion.
- **Right-to-left.** Not mirrored. `side` does not follow `dir`, and positions are physical: the container is pinned with `left`/`right`, menu text is left-aligned, and badges and actions sit at the right edge. A `dir` passed to `<Sidebar>` reaches only the phone drawer.
- **Layering.** On desktop a collapsible sidebar is `fixed` at `z-10` and its rail at `z-20`.

It does not include navigation content, routing or active-link detection, a collapsible sub-menu, a topbar or breadcrumb, or a server-side read of the cookie. `admin-01`'s own `admin-sidebar.tsx` and `admin-topbar.tsx` show a full composition and are not part of the item.

While adapting it we also fixed a hydration bug present upstream: `SidebarMenuSkeleton` calls `Math.random()` in a `useState` initialiser, so the server and the client pick different widths.

## Chat and agent UI come from shadcn

Keystone does not ship chat components. shadcn's — `MessageScroller`,
`Message`, `Bubble`, `Attachment`, `Marker`, and the AI Elements compositions
built on them — are Base UI, read the same semantic tokens, and work in a
keystone app:

```bash
npx shadcn@latest add message-scroller message bubble attachment marker
```

Run it **after** keystone's components are installed and never with
`--overwrite`. The chat items depend on shadcn's `button` and friends, and an
existing keystone file at the same path is what keeps them composing keystone's
Button rather than replacing it.

They style themselves with utilities from `shadcn/tailwind.css`, which
`shadcn init` imports. If your project started from `pnpm add
@keystoneui/react` instead, add it next to keystone's:

```css
@import "tailwindcss";
@import "shadcn/tailwind.css";
@import "@keystoneui/react/base.css";
```

The two stylesheets do not collide. Keystone's own utilities are namespaced —
`ks-typeset`, `ks-scroll-fade`, `ks-shimmer`, `ks-scrollbar` — because shadcn
defines `scroll-fade` and `shimmer` too, and Tailwind applies *both* rules when
two `@utility` blocks share a name. A test reads the installed
`shadcn/tailwind.css` and fails if a keystone name ever overlaps again.

## Vendoring base.css

`@keystoneui/react/base.css` is the one runtime file a registry install still
imports from the npm package. To drop the dependency, copy it into your project
and import the copy instead:

```bash
cp node_modules/@keystoneui/react/src/base.css src/styles/keystone-base.css
```

```css
@import "./styles/keystone-base.css";
```

You then own it: future fixes to motion tokens, popup layering or the
utilities above reach you only when you copy it again.
